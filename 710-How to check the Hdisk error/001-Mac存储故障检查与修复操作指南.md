## 一、先分清资料保护与机器验收
**有重要资料时先保资料；明确是可清空的测试机时，才逐级增加写入和重建测试。**

| 状态 | 合理的第一步 |
| --- | --- |
| 重要资料没有其他副本，磁盘仍能稳定读 | 先复制关键资料并验证副本；再做结构检查 |
| 反复掉盘、读取时卡死，或机械盘出现异响 | 停止反复扫描和写入；按资料价值考虑专业恢复 |
| 没有重要资料的测试机 | 可安排独立文件写入验证；抹盘重建是另一步操作 |
| 外接盘异常 | 同时记录线缆、盒子、接口和供电；换一条可靠链路复核 |

急救会在需要时改写文件系统元数据。它不是数据恢复软件。不存在“检查得越狠越安全”的通用规则；已经确认读盘不稳定时，不把长扫描当成备份的替代品。

本指南主要覆盖 Apple 芯片 Mac、内置 SSD 和 APFS；外接盘、HDD、RAID、NTFS、exFAT 的命令及诊断不能整套照搬。

## 二、确认目标和磁盘层级
先在目标电脑终端运行：

```sh
hostname
/usr/bin/sw_vers
/usr/sbin/diskutil list
/usr/sbin/diskutil info /System/Volumes/Data
/usr/sbin/diskutil apfs list
```

本例层级如下，仅用于认路，编号不作为通用命令：

```text
APPLE SSD AP0256Q Media         物理设备，约251GB
└─ 主 APFS 容器                 约245GB，本次编号disk3
   ├─ Macintosh HD 宗卷组
   │  ├─ Macintosh HD           系统卷
   │  └─ Macintosh HD - Data    数据卷，本次disk3s1
   └─ Preboot / Recovery / VM等

Apple disk image Media          恢复环境磁盘映像
└─ 另一个 APFS 容器             本次约1.85GB、disk5
   └─ macOS Base System
```

核对五项：主机名、设备型号、容量、数据卷 UUID、物理存储与容器对应关系。IP 相同不保证还是同一台电脑；卷同名也不保证是同一个卷。

恢复模式中的设备编号可能变化。FileVault 锁定与卷未装载是状态，不应直接当作损坏；使用本机登录密码解锁，不把密码贴进聊天或日志。Data 卷显示 `Sealed: No` 本身也不是故障；不要把系统卷的密封要求套到数据卷上。

## 三、保存在线检查的完整证据
### 1. 采集目录和输出
下面在要检测的 Mac 上运行。输出路径应位于可靠、空间足够的介质；有疑似严重故障的盘时，把 `check_out` 改到另一块健康存储。

```sh
check_out="$HOME/storage-check-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$check_out"
/usr/sbin/diskutil info /System/Volumes/Data > "$check_out/data-info.txt" 2> "$check_out/data-info.stderr"
/usr/sbin/diskutil apfs list > "$check_out/apfs-layout.txt" 2> "$check_out/apfs-layout.stderr"
/usr/sbin/diskutil verifyVolume /System/Volumes/Data > "$check_out/data-verify.txt" 2> "$check_out/data-verify.stderr"
check_rc=$?
printf '%s\n' "$check_rc" > "$check_out/data-verify.exit-code.txt"
```

这是检查命令，不是 `repairVolume`。启动卷通常无法在线卸载，工具可能使用 live verification；校验时界面可能短暂不响应。准备运行前先保存正在做的工作。

不要通过 `命令 | tail` 后的 `$?` 推断原命令是否成功；那通常是管道末端命令的状态。也不要用 `2>/dev/null` 把权限或不支持错误藏起来。

### 2. 继续检查容器及分区表
从本次 `diskutil info` 的 `APFS Container` 字段取得容器编号，人工核对后执行。以下占位符必须替换，不能直接照抄：

```sh
/usr/sbin/diskutil verifyVolume diskN
/usr/sbin/diskutil verifyDisk diskM
```

`diskN` 表示包含目标数据卷的 APFS 容器；`diskM` 表示其物理整盘。`verifyDisk` 主要校验分区表，不能代替文件系统、全盘读取或 SSD 健康检查。

### 3. 怎么看结果
同时查看退出码、完整 stdout、stderr 和原警告是否重复。`fsck_apfs` 手册说明，默认只有警告而无错误时也可退出 0；不能只看最后一行。→ 案例附存的 `fsck_apfs 手册`（原库附件/证据，未包含在本测试包） · `-n`、`-l`、`-W`。

出现 `Try running fsck against the entire APFS container` 时，把整个容器纳入下一步。若在线容器校验也复现，不等于已经修复；应转入恢复环境处理。

## 四、读取 SSD 健康信息
系统概览中的 SMART Verified 只是基础状态，能读取时继续保存详细健康页。

已安装 smartctl 时，先确认版本和设备，再运行；`/dev/diskM` 是本次核对的物理设备：

```sh
smartctl --version
smartctl -i -H -A -j /dev/diskM > "$check_out/smart-health.json" 2> "$check_out/smart-health.stderr"
smart_rc=$?
printf '%s\n' "$smart_rc" > "$check_out/smart-health.exit-code.txt"
```

没有该工具时，可以选择从可信的软件源安装 smartmontools，或使用可信的临时程序；不要为了“能读到”而随意装内核驱动、放宽系统安全或改磁盘权限。权限不足时在本机处理必要授权；不索要用户密码。

| NVMe 字段 | 可以怎样用 | 不应怎样解释 |
| --- | --- | --- |
| Critical Warning | 看当前警告位；非零时逐项解码 | 0不等于所有硬件都好 |
| Media and Data Integrity Errors | 保存累计值，比较前后变化 | 单次非零不直接定位全部原因；新增长要重视 |
| Available Spare | 看备用资源比例及门槛 | 不是Finder显示的剩余磁盘空间 |
| Percentage Used | 视为固件的耐久消耗估计 | 1%不等于精确测得健康度99% |
| Unsafe Shutdowns | 结合历史与近期增量看 | 不是坏盘计数，也不是故障根因证明 |
| Power On Hours | 保存原始通电计数 | 不能直接换算整机购买时间或成色 |

这些字段跨 SATA、NVMe、外接桥接芯片并不通用。优先查当前工具手册、设备与驱动支持情况。→ [smartctl 官方手册源码](https://github.com/smartmontools/smartmontools/blob/main/src/smartctl.8.in)；本目录案例的实际 JSON。

本次 `smartctl -a -j` 曾因为详细错误日志 GetLogPage 读取失败而返回 4，但健康页已读出；缩小为 `-i -H -A -j` 后返回 0。应保留两份结果，不能把工具/API 读取失败当成介质错误，也不能把读到健康页说成读到了详细错误日志。`smartctl` 退出状态按位编码，值4不是4次坏块。→ [smartctl 官方退出状态说明](https://github.com/smartmontools/smartmontools/blob/main/src/smartctl.8.in) · EXIT STATUS。

## 五、需要时做数据完整性测试
**只在资料已保护、设备当前稳定且愿意承担测试写入时做。** 先接电，保存工作、记录后台负载和空间，使用独立测试目录。不要在日常资料文件上覆盖测试模式。

### 1. 文件级写入与读回
本次成功执行的方法：新建32GiB文件，用偏移相关数据填充；同步落盘后完整读回，逐字节比较；更换种子重写并复验；再随机抽取8192个4KiB块核对。

记录测试体积、轮数、同步方式、缓存处理、随机次数、错误偏移和退出码。成功后只清理本程序创建的临时文件；失败时保留日志，停止继续加压。

本目录保存的是当次使用的源码，参数固定，不适合对所有容量的盘直接运行。详见 [004-工具与证据使用说明](004-%E5%B7%A5%E5%85%B7%E4%B8%8E%E8%AF%81%E6%8D%AE%E4%BD%BF%E7%94%A8%E8%AF%B4%E6%98%8E.md)。F_NOCACHE、fsync、F_FULLFSYNC 降低缓存造成的误导，但未经过重启后读回，就不能声称测过持久性或断电保护。

### 2. 全盘逻辑只读
这是可选增强项：能发现逻辑地址读取报错，却不能验证原内容是否正确，也不覆盖控制器隐藏的全部物理NAND。本次目标机没有执行，不把另一台电脑的全盘读取结果算给它。

仅在已经核对目标、具有原始设备读取权限且资料状态允许时，在目标电脑本机运行。把 `rdiskM` 换为本次物理整盘：

```sh
sudo /bin/dd if=/dev/rdiskM of=/dev/null bs=8388608
```

这里 `if=` 是待读设备，`of=/dev/null` 固定为丢弃输出。**本指南不提供向原始设备写入的 dd 命令。** 权限不足时不要改组成员、关闭安全功能或绕路提权。保存实际完成字节数、时间和退出码；只完成部分不能写成全盘通过。

### 3. 日志配合
在目标 Mac 上运行并保留完整输出：

```sh
/usr/bin/log show --last 1h --style compact --predicate 'process == "kernel" AND (eventMessage CONTAINS[c] "I/O error" OR eventMessage CONTAINS[c] "ANS Recover" OR eventMessage CONTAINS[c] "nvme timeout" OR eventMessage CONTAINS[c] "checksum mismatch")'
```

使用绝对路径 `/usr/bin/log`，避免本机同名命令遮蔽。无匹配只说明保留时段和检索条件内未命中，不是整机无故障证明。测试前后对照计数，既有累计错误与新增错误分开记录。

## 六、进入恢复模式执行急救
### 1. 启动与识别
Apple 芯片 Mac：关机，持续按住电源键至启动选项，选择“选项→继续”；需要时用电脑登录密码认证。进入磁盘工具，选择“显示→显示所有设备”。Intel Mac 的启动方式不同，另查对应官方说明。→ [Apple 芯片 Mac 的恢复环境](https://support.apple.com/guide/mac-help/macos-recovery-a-mac-apple-silicon-mchl82829c17/mac)；本次实际操作照片。

在完整层级中确认内置物理设备及其主容器，不能把小容量 `macOS Base System` 磁盘映像当成目标。选中后先看名称、容量和层级，再点击急救；底部设备编号只作当次参考。

### 2. 操作顺序
按当前设备的实际层级，从最下面的卷开始向上处理：**卷→卷组（若可选）→容器→物理设备**。每一步急救完成后展开细节，遇到错误先保存，不立即重复点击。按钮不可用时按工具及官方说明处理，不凭猜测强行卸载。→ [Apple 磁盘急救流程](https://support.apple.com/en-us/102611) · Use First Aid。

数据卷加密时按提示解锁。运行前确认弹窗中的目标名称；“是否运行”的确认框不是结果页。完成页的绿色勾号也只证明本次操作结束，需要继续读日志。

本次目标机先对数据卷运行急救，仍提示需检查整个容器；再对主容器急救，最后重启复查才确认原警告消失。没有证据表明本次用户还对物理整盘执行过恢复模式急救，因此不能把完整建议流程写成全部已做。

### 3. 留存结果
拍到或保存：目标名称、执行命令/模式、警告所在段落、修复动作和最后结果。长日志分上中下拍摄，保留时间顺序；不能只拍最后一屏。

这次恢复模式数据卷日志显示 `fsck_apfs -y -x`，卷已卸载；它与正常系统中的 `-n -l` 在线校验不是同一种操作。前者可能修改元数据，后者是检查。不要在已挂载的启动盘上照抄底层 `-y` 命令。

## 七、重启后验证修复结果
重新进入正常桌面，重新识别磁盘和数据卷 UUID，再做第三章的数据卷与主容器检查。比较的是同一卷的新结果，不只比较名称。

验收至少回答：

- 原来的同一对象警告是否消失？
- 有无新警告、错误或跳过的卷？
- 退出码是否正常，完整 stdout/stderr 是否支持结论？
- 正常使用、文件操作和后续重启后是否复发？

本次目标机在18:32重启后，两项检查均无原警告。可以写“原问题经急救后复查已消失”，不能写“永久修复、SSD绝无隐患”。后续何时复查按症状、使用和退换期限决定，不机械地反复全盘测试。

## 八、仍未解决时怎样升级检查
| 后续表现 | 下一步 |
| --- | --- |
| 在线警告，离线急救后消失，无读写错误 | 正常使用后复查，记录是否复发 |
| 急救提示查容器，尚只修了数据卷 | 补做正确容器层级的离线急救 |
| 急救失败或问题快速复发 | 检查详细健康/错误计数，结合服务方诊断；别继续只看绿色勾号 |
| 介质错误增长、实际数据读回不一致、持续掉盘 | 优先保护资料，停止反复写入，排查存储/控制器/内存及外接链路 |
| 明确允许清空的测试机仍有结构问题 | 保留旧证据后，可另行选择重建APFS和重装，清洁系统先不恢复旧配置再测 |

重新安装系统、抹掉卷组、删除容器、抹掉物理盘、“抹掉所有内容和设置”并不等价，必须写明实际范围。不要默认抹掉设备内的隐藏恢复/启动分区。涉及重建时另按该机型的官方重装流程执行，不用一条硬编码 `eraseDisk` 命令解决所有机器。

“测试机、无重要资料”允许扩大检查选择，但不自动等于授权删除账户、软件、容器和激活状态。目标机此次问题已消失，没有为此执行抹盘重装。

## 九、远程协作与照片取证
正常系统可用SSH采集与复测；本次进入恢复模式后没有可用的SSH控制通道，需要用户现场启动、解锁及点击。不要先承诺可以全程无人值守修启动盘。

手机辅助时先核对序列号，只有无线通道实际读取成功后才告知可以拔线。照片按时间排序；用户说“连续几张”就读最新3—5张，不能只盯最新一张重复索要。照片不足以确认时，优先通过重启后的原始日志补证，不无限重复拍照。

原始照片与系统日志可能包含设备标识、账户和路径；本地保留原件，对外分享先检查内容。

## 十、结论怎么写才准确
推荐格式：

> 在某日期、某设备及卷UUID上，以某方式检查；观察到什么，采取什么处理，重启后复查得到什么；还有哪些项目没覆盖。

避免“没有坏道”“原装无修”“100%健康”“一次通过永久稳定”。SMART、结构校验、数据完整性、实际体验应分别给结论，不能拼成一个没有依据的总分。
