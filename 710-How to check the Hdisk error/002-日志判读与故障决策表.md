## 一、常见输出怎么理解
| 输出或现象 | 可以确认什么 | 下一步与边界 |
| --- | --- | --- |
| `appears to be OK` / 退出0 | 工具本次没有以失败状态结束 | 仍阅读全文，默认可能容许warning |
| `minor issues that can be repaired` | 工具报告可修复的结构问题 | 不等于已修复，也不等于SSD坏了 |
| `Unable to perform deferred repairs...` | 所需延迟修复未完成 | 看后文是否要求完整容器检查 |
| `Try running fsck against the entire APFS container` | 单卷范围不足以完成所需处理 | 核对层级，安排整个容器的离线急救 |
| `A repair action has been taken...` | diskutil打印了这条提示 | 对照执行模式、fsck记录及后续复查，不能单独当成功证据 |
| `repairs=0` | 对应那次fsck记录未计入修复 | 匹配时间与设备；不能拿在线记录否定另一次离线修复 |
| `SMART Verified` | 系统提供的基础健康判断 | 补充详细指标和实际读写校验 |
| `Permission denied` / 密码要求 | 当前权限不够 | 不把未读到写成不存在，不关闭安全功能绕过 |
| `GetLogPage failed` | 某日志页未读成功 | 核对API/支持情况、保留stderr和可读取字段 |
| `self_test=false` | 当前设备接口声明不支持该能力 | 不宣称已经执行NVMe长自检 |
| 原警告消失 | 当前复查未再复现该警告 | 核对同一卷身份，继续按需观察复发 |

→ 目标机 `fsck_apfs手册`（原库附件/证据，未包含在本测试包）；[smartctl手册](https://github.com/smartmontools/smartmontools/blob/main/src/smartctl.8.in)；[003-目标机APFS故障修复实录](003-%E7%9B%AE%E6%A0%87%E6%9C%BAAPFS%E6%95%85%E9%9A%9C%E4%BF%AE%E5%A4%8D%E5%AE%9E%E5%BD%95.md)。

## 二、证据组合怎样决定下一步
| 结构检查 | 健康与实际读写 | 合理判断 |
| --- | --- | --- |
| 有可修复警告 | 暂无介质错误、抽样读回正确 | 先修结构，不直接判坏盘 |
| 修复后无警告 | 抽样测试通过 | 本轮可验收项目通过；仍保留范围限制 |
| 持续复发或无法修复 | 健康读数正常 | 硬件、固件、系统原因都还没排除，继续隔离 |
| 无结构警告 | 读回不一致或介质错误新增 | 不能因文件系统通过就忽略数据路径问题 |
| 工具未能读取 | 没有可用数据 | 明确写“未完成”，不要补成“正常” |

判定硬件问题时，数据读回不一致仍需考虑内存、控制器和外接链路等原因，不能仅凭一个软件测试定位到某颗NAND。

## 三、本次最容易误读的四段日志
### 1. 两次出现同一警告
```text
inode (id 223782)
INO_EXT_TYPE_PURGEABLE_FLAGS
```
这是同一文件对象的元数据线索，不是“223782个坏块”。它不足以告诉我们该文件的路径、内容是否损坏、谁造成了问题。本次路径查询返回权限不足，没有据此删除对象。

### 2. 操作成功但修复未完成
数据卷急救照片同时出现“操作成功”和“需要对整个容器检查”。正确处理是继续容器层级，而不是用绿色勾号覆盖文本。

### 3. 在线和离线不是同一次操作
本次在线输出有 `-n -l`，日志记 `repairs=0`；恢复模式数据卷照片显示 `-y -x`、卷已卸载。不同时间、不同模式的记录分别解释。

### 4. 照片先后顺序影响结论
18:10数据卷警告 → 18:20容器急救完成 → 18:32重启后数据卷和容器无警告。不能用18:10照片证明18:20之后仍有原问题；也不能只看18:20最后一屏证明原警告已清除。最终由18:32原始复查输出补足。

## 四、哪些情况先停止加压
发现读写内容不一致、持续I/O报错、设备反复消失、文件读取迅速恶化，或工具明确无法完成时，先保全日志和可读资料，再决定恢复或维修。不要反复格式化、重试写满、强制断电来“看看能不能恢复”。

对稳定测试机，单一可清理标志警告没有必要自动升级成全盘破坏性测试。本次修复后原警告消失，下一步是观察与按需复测，不是继续增加测试轮数来追求无法证明的绝对安全。
